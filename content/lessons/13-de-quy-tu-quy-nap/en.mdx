## 1. Opening problem

> Prove that $1 + 2 + \dots + n = \dfrac{n(n+1)}{2}$ for every positive integer $n$.

You write it at once: true for $n = 1$. Assume it for $n = k$, so $1 + \dots + k = \frac{k(k+1)}{2}$. Then

$$1 + \dots + k + (k+1) = \frac{k(k+1)}{2} + (k+1) = \frac{(k+1)(k+2)}{2}$$

matching the formula for $n = k+1$. Done.

Now look back at that proof. It has **two parts**: one case you can settle immediately, and a rule reducing a larger case to a smaller one.

That is exactly the structure of a recursive function.

## 2. The mathematical idea

Put them side by side:

| Mathematical induction | Recursive function |
| --- | --- |
| Base: prove it for $n = 1$ | Base case: return a value immediately |
| Step: from $k$ deduce $k+1$ | Recursive call: use the result for $n-1$ |
| Conclusion: true for all $n$ | The function is correct for all $n$ |

This is not a metaphor. Proving a recursive function returns the right value **is** an induction proof, word for word.

For instance, to prove that

```python
def total(n):
    if n == 1:
        return 1
    return n + total(n - 1)
```

returns $\frac{n(n+1)}{2}$, you write: true for $n = 1$ since it returns 1. Assume it for $n-1$, so `total(n-1)` returns $\frac{(n-1)n}{2}$. Then `total(n)` returns $n + \frac{(n-1)n}{2} = \frac{n(n+1)}{2}$. Done.

<Note>
Since the two are one thing, every familiar mistake in induction has a twin in recursion. Forgetting the base case in a proof leaves the statement without a foundation; forgetting it in code makes the function call itself forever until the stack overflows. One mistake, two symptoms.
</Note>

## 3. Turning it into an algorithm

Writing a recursive function means answering three questions, in this order:

1. **What is the base case?** The smallest case you can answer without calling yourself.
2. **What is the smaller subproblem?** It must genuinely be smaller, by some quantity that always decreases. This is the termination condition from lesson 1.
3. **How do the small results combine into the large one?**

Applied to the Towers of Hanoi, moving $n$ disks from peg A to peg C using B:

1. Base: $n = 0$, do nothing.
2. Smaller problem: move $n-1$ disks.
3. Combine: move the top $n-1$ from A to B, move the largest from A to C, move $n-1$ from B to C.

The move count satisfies $T(n) = 2T(n-1) + 1$ with $T(0) = 0$, giving $T(n) = 2^n - 1$. Lesson 14 teaches how to solve recurrences like this.

## 4. Simulation

This lesson has no simulation of its own. Trace the Hanoi function by hand for $n = 3$ and write out the tree of calls. You will find it has 7 leaves, exactly $2^3 - 1$ moves.

## 5. Pseudocode and Python

```python
def hanoi(n, source, target, spare):
    if n == 0:
        return
    hanoi(n - 1, source, spare, target)      # move n-1 disks to the spare peg
    print(f'Move disk {n}: {source} → {target}')
    hanoi(n - 1, spare, target, source)      # move n-1 disks from spare to target

hanoi(3, 'A', 'C', 'B')
```

Worth noticing: you do not need to picture all 7 moves to write this. You only need to trust that the call `hanoi(n-1, ...)` does its job. That trust is precisely the induction hypothesis.

Being able to write code without imagining the whole process is what makes recursion powerful, and also what makes it uncomfortable at first.

## 6. What to take away

If you have ever completed an induction proof, you already know recursion. The only thing to change is the **direction of thought**: induction climbs from small to large, while writing a recursive function you stand at $n$ and call down to $n-1$.

Up or down, the structure is identical, and that difference of direction is exactly the subject of lesson 19, where dynamic programming turns out to be recursion written the other way round.
