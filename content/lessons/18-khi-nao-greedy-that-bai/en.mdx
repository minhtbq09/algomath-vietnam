## 1. Opening problem

Lesson 17 ended with a coin-change problem where greedy worked perfectly. Now change the coin system.

> An imaginary country has coins of 1, 3 and 4. Pay 6 using as few coins as possible.

Greedy: take a 4, leaving 2, then two 1s. **Three coins**.

But $6 = 3 + 3$, only **two coins**.

The algorithm from the previous lesson just returned a wrong answer. It did not crash, it did not misbehave, it simply was not optimal. And if you only ever tested it on Vietnamese currency, you would never find out.

## 2. The mathematical idea

What broke? Go back to the two properties from lesson 17.

The "greedy choice is safe" property says some optimal solution contains the first greedy choice. Here the greedy choice is a 4, but the only optimal solution is $3 + 3$, which contains **no** 4. The property is violated, so the conclusion collapses.

Why does Vietnamese currency work then? Because it has a special structure: each denomination is a multiple of the previous, or nearly so. Such systems are called **canonical**, and for canonical systems greedy is provably optimal.

The system 1, 3, 4 is not canonical, so greedy breaks.

<Note>
This is the deepest lesson of chapter 5. An algorithm is not absolutely correct or incorrect. It is correct **under some assumptions**. When you use greedy, you are implicitly asserting that your data satisfies those assumptions. If you do not know what they are, you do not know what you are asserting.
</Note>

## 3. Turning it into an algorithm

So what is the right procedure when facing an optimisation problem?

1. **Think of a greedy rule.** This is usually easy, and intuition usually points the right way.
2. **Try to find a counterexample.** Spend real time here. Try boundary cases, close values, and small datasets you can solve exhaustively by hand.
3. **If no counterexample turns up, try to prove it** with the exchange argument from lesson 17.
4. **If you cannot prove it, switch to dynamic programming.** DP is slower but assumes nothing about the structure of the problem.

The most effective way to find a counterexample is **differential testing**: write a slow but certainly correct exhaustive function, then compare it against greedy on thousands of small random inputs. That finds counterexamples far faster than sitting and thinking.

## 4. Simulation

This lesson has no simulation of its own. The most effective self-check is running the code in section 5, which finds the counterexample for you.

## 5. Pseudocode and Python

```python
def greedy_change(coins, amount):
    count = 0
    for c in sorted(coins, reverse=True):
        count += amount // c
        amount %= c
    return count if amount == 0 else None

def optimal_change(coins, amount):
    """Exhaustive, slow but certainly correct. Used as the reference."""
    f = [0] + [float('inf')] * amount
    for t in range(1, amount + 1):
        for c in coins:
            if c <= t:
                f[t] = min(f[t], f[t - c] + 1)
    return f[amount] if f[amount] != float('inf') else None

# Find counterexamples automatically
coins = [1, 3, 4]
for amount in range(1, 30):
    g = greedy_change(coins, amount)
    o = optimal_change(coins, amount)
    if g != o:
        print(f'{amount}: greedy uses {g} coins, the optimum needs only {o}')
```

Running this prints 6 and several other values. The `optimal_change` function is dynamic programming, the subject of lesson 19.

## 6. What to take away

Greedy intuition is usually right, but "usually right" is not a mathematical property.

The habit to build: every time you think of a greedy rule, **spend a few minutes trying to break it before trusting it**. If you cannot break it and cannot prove it either, use dynamic programming and sleep well.
